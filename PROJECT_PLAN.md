# P2P Payment Ledger — Project Plan

## Project Overview

The P2P Payment Ledger is a simulated digital wallet application that enables peer-to-peer money transfers using an ACH-style delayed settlement model. Users register, load virtual funds, transfer money to other users, and track transaction history. The system enforces fraud detection rules, runs background settlement and housekeeping jobs, and provides an admin monitoring panel.

The application also includes **Check Please** — a merchant-specific payment-intent reservation feature inspired by CRED.ai. A user declares intended payment to a registered merchant with a maximum amount and a chosen expiry. The system recognizes eligible payments associated with that reservation and applies adjusted merchant-risk handling, while all critical security controls remain mandatory.

This is a **simulated educational wallet** and is not intended for production use as a regulated payment service.

---

## Goals

1. Implement a fully functional P2P wallet with delayed ACH-style settlement.
2. Enforce fraud controls: daily limits, duplicate detection, high-value flagging.
3. Provide a Check Please feature with atomic reservation and payment lifecycle.
4. Deliver a React frontend for all user and admin workflows.
5. Ensure financial correctness: no partial state, no duplicate debits or credits, idempotent retries.
6. Maintain comprehensive audit and job logging for all admin and scheduled operations.

## Key Technical Risks

### R-001 — BigDecimal / NUMERIC Consistency
**Risk:** Using `float` or `double` anywhere in the money calculation stack causes silent rounding errors.
**Mitigation:** Enforce `NUMERIC(19,4)` in all PostgreSQL monetary columns; enforce `BigDecimal` in all Java money fields; use `HALF_UP` rounding for all arithmetic. The Kiro steering instructions enforce this rule in every session.

### R-002 — Concurrent Reservation Consumption
**Risk:** Two simultaneous merchant payment requests for the same reservation may both succeed, double-debiting the wallet or over-consuming the reservation.
**Mitigation:** Use `SELECT FOR UPDATE` on the wallet row and the reservation row inside a single `@Transactional` block during payment capture. Enforce `UNIQUE` constraint on `merchant_payments.request_id` for idempotency. Implement concurrency tests in Phase 7.

### R-003 — Business Day Calculation and Holiday Calendar
**Risk:** The settlement due date calculation (T+3 business days) may give incorrect dates if the holiday calendar is not specified.
**Mitigation:** Pending resolution of **OD-001**. Until resolved, implement weekends-only exclusion as default. Document the policy in code and in the ARCHITECTURE file. The `BusinessDayCalculator` utility must be easy to swap in the holiday list.

### R-004 — Settlement Job Atomicity and Idempotency
**Risk:** If the settlement job crashes mid-run, some transfers may be settled but not logged; on restart, re-processing could double-credit receivers or double-refund senders.
**Mitigation:** Use `@Transactional(propagation=REQUIRES_NEW)` per transfer in the settlement loop so each transfer commits or rolls back independently. Use the transfer `status` field as an idempotency guard — only process transfers in `PENDING` state. Test refund idempotency explicitly in Phase 8.

### R-005 — JWT Secret Management
**Risk:** Committing the JWT signing secret to source control exposes all tokens to compromise.
**Mitigation:** JWT secret must be read from an environment variable (`JWT_SECRET`). The `application.properties` file must reference it as `${JWT_SECRET}`. The secret is never hard-coded or logged. The `.gitignore` must exclude any `.env` file.

### R-006 — Java 25 Toolchain Compatibility
**Risk:** Spring Boot 4.1.2 is confirmed. The risk is now Java 25 toolchain compatibility: Lombok, Jakarta annotation processors, and other APT-based tools must be compatible with Java 25. Java 25 may require the `--enable-preview` flag.
**Mitigation:** T-010 verifies Maven resolution, Java 25 compiler target, and annotation processor compatibility before any domain code is written. If incompatibility is found, stop and report.

## Open Decisions

All six open decisions have been resolved. No items require user approval before implementation.

| ID     | Phase Affected | Resolution |
|--------|---------------|------------|
| OD-001 | Phase 8       | **RESOLVED** — Weekends-only exclusion (Saturdays and Sundays). No public holiday calendar without explicit user approval. |
| OD-002 | Phase 8       | **RESOLVED** — Asia/Kolkata (IST, UTC+5:30) for all scheduled jobs. DB timestamps stored as UTC. No DST. Cron expressions use `zone = "Asia/Kolkata"`. |
| OD-003 | Phase 7       | **RESOLVED** — Reservation expiry: min 1 hour, max 30 days from creation time. Both limits configurable in `application.properties` via `check.please.reservation.expiry.min-hours` and `check.please.reservation.expiry.max-days`. |
| OD-004 | Phase 6 / 7   | **RESOLVED** — Mandatory controls always active for merchant payments (JWT, ownership, PIN, wallet status, merchant identity, account lock, idempotency). P2P daily ₹50,000 limit, duplicate-transfer rule, and high-value ₹8,000 alert do NOT apply to merchant payments. Implemented as separate `checkMerchantPayment()` method. |
| OD-005 | All phases    | **RESOLVED** — INR (₹). BigDecimal in Java, NUMERIC(19,4) in PostgreSQL. Thresholds: ₹50,000 daily P2P limit; ₹8,000 high-value P2P alert. |
| OD-006 | Phase 1       | **RESOLVED** — Spring Boot 4.1.2 + Java 25 confirmed. T-010 verifies Maven resolution, Java 25 compiler target, and annotation processor compatibility (Lombok, Jakarta validation). |
